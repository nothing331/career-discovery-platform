Implementation proposal / 25 October 2026

Germany data POC

Collect official study information, preserve its evidence, and make the resulting dataset easy to inspect.

Version 1.0 · Stakeholder summary + technical implementation + cost assumptions

Build one small, complete collection loop before expanding coverage. The first POC runs on an existing laptop, stores data locally, and uses a low-cost model only where ordinary parsing is insufficient. It supports Indian students considering German bachelor’s and master’s routes, with the rules kept separate.

3 universities
Initial source coverage target
~10 programmes
Both degree levels represented
$5 API cap
Proposed run budget · $0 hosting
The decision: start with Python + SQLite + local files + a Streamlit review browser. Benchmark Qwen 3.7 Flash as the default paid extractor. Keep model providers replaceable. These are proposed implementation choices, not measured performance or a production release.
02

What the POC will show

A colleague should be able to browse real programme records, inspect where each value came from, and see what the pipeline could not establish.

For the team

  • A local programme catalogue with fees, deadlines and requirements.
  • Source links, supporting passages, quality reasons and review status on each important fact.
  • Visible missing data, conflicts and source failures.
  • A repeatable refresh, change history and per-run cost report.

Initial boundaries

  • Germany as destination; India as the initial applicant context.
  • Three universities, roughly ten programmes and at most 50 source documents in the first run.
  • Separate bachelor’s/master’s rules and explicitly named intakes.
  • Source-backed programme exploration; an admissions or visa guarantee is outside this POC.

City costs, scholarships, employment/salary data, transcript uploads and student accounts are later modules. The initial POC proves acquisition and evidence quality. Ten programme records do not establish national coverage or student demand.

Example question the data should support: “For this programme and intake, what requirements and costs are explicitly stated, and what still needs checking?” Missing information must never silently become a zero fee or an eligibility rejection.

03

How collection will work

The first official institution and programme URLs are selected manually. Link discovery, collection, extraction and repeat runs are then automated within the approved scope.

  1. Register sourcesRecord the responsible publisher, official domains, relevant fields, access/reuse conditions and collection limits.
  2. Discover URLsRead sitemaps and catalogues. Follow programme, admission, fee and regulation links through a bounded source adapter.
  3. Fetch & archiveUse HTTPX for HTML/PDF. Use Playwright only for content that requires JavaScript. Save bytes, headers, timestamps and hashes.
  4. Parse & extractSelectors handle structured fields. Local PDF parsing handles text/tables. Qwen proposes typed claims from relevant prose sections.
  5. Validate & reviewCheck schema, evidence, units, scope and conflicts. Preserve failures; review critical fields before publication.
  6. Publish & refreshWrite approved facts, show their evidence, track coverage, and reprocess only changed inputs or changed extraction versions.

Bounded discovery, not an unrestricted web agent

Each university adapter supplies catalogue URLs, selectors and allowed link rules. Domains, depth and document counts are capped. External links become candidates for source review rather than automatically extending the crawl. Search can later help discover sources; a search snippet is not evidence for a published fact.

Use the university’s own programme pages and regulations for programme rules; use the responsible official authority for applicant/visa procedures. An aggregator’s availability does not automatically grant permission to mirror its catalogue. Public access, robots rules and reuse rights are separate source checks.

Collection defaults

One active request per host, a three-second delay, four HTTP tasks across hosts, a 30-second HTTP timeout and at most two retries after the initial attempt. PDF parsing starts with one worker. Respect longer published delays and retry instructions. Blocked or unsupported sources remain visible in the coverage report.

Model choice and API contract

Proposed primary model: qwen3.7-flash-2026-07-15, using Alibaba’s Singapore/international deployment. Use JSON Schema output and validate it again with Pydantic. Qwen’s current documentation lists the model family under JSON Schema support. Provider support and schema compatibility need a real smoke test before the first data run. [S2]

Gemini 3.1 Flash-Lite is the comparison/fallback candidate. DeepSeek Flash is another candidate. A small local Qwen model is an optional zero-per-token-cost experiment after checking available memory; it is not the default build dependency. Choose by correct, grounded results and review effort, not token price alone.

05

Storage, evidence and repeat runs

SQLite is the cheapest starting point for a single worker. Logical table groups keep raw evidence, candidate claims and approved knowledge separate. They become Postgres schemas when multi-worker or shared access is needed.

LayerInitial locationContents
Source archivedata/raw/Versioned HTML/PDF bytes, subject to source-specific retention/reuse conditions
Parsed evidencedata/parsed/Text, tables, section IDs, page/DOM locations and parser version
Operationsops_* tablesSources, URLs, fetch attempts, snapshots, jobs, extraction runs and spend
Candidate claimsstaging_* tablesTyped candidates, evidence, scores, conflicts and review decisions
Published knowledgekb_* tablesInstitutions, programmes, intakes, fees, requirements, policies and fact history

Use stable internal IDs and a reviewed alias map. A programme belongs to an institution and campus; intake- and applicant-specific claims must not be collapsed into a single university-wide value. Store observed_at separately from stated effective dates. Money uses decimal-safe values and explicit units/periods.

Every non-null published critical value must link to a reviewed candidate and snapshot. Missing source text remains unknown. Preserve AND/OR test alternatives, fee exemptions and other conditions instead of flattening them into unrelated mandatory rules.

Refresh without paying for the same extraction again

Use ETag/Last-Modified where supported and hash each snapshot. Cache extraction by parsed-content hash + parser version + schema version + prompt version + model configuration. Reuse a successful result only when that fingerprint matches. Keep fetch timestamps even on unchanged content; a recent fetch alone does not prove a rule is effective for a future intake.

Changed content produces new candidates and an audit diff. Old evidence remains available under the retention policy. Failed refreshes and overdue checks mark affected facts stale; they must not silently become current. A newer low-authority claim cannot overwrite a verified rule simply because it is newer.

Run refresh manually during development. The local process only runs while the laptop is on. Later, schedule due targets with a single worker and persisted jobs; introduce a server when unattended runs or shared access are needed. Migration to Postgres through SQLAlchemy still requires tested migrations and queries. A separate vector database is not required for this POC.

06

Confidence that can be explained

Score individual claims, not entire websites or programmes. A university may be authoritative for its own fee but not for another institution’s admissions. The model proposes claims; application code and reviewers decide whether they are published.

30 authority25 evidence grounding20 applicability15 freshness10 verification

Initial rubric: multiply each weight by a documented component value between 0 and 1; store the component reasons and rubric version. A score of 90 is a heuristic quality rating, not “90% likely to be correct.” Calibrate using the manually checked sample. Repeated copies of one source are not independent corroboration.

Automatic checks

  • Valid schema, types, units and normalization.
  • Exact/normalized quote resolved to a stored text location.
  • Value and conditions supported by the surrounding evidence.
  • Programme, applicant group, degree and period match.
  • No unresolved same-scope critical conflict.

Publication gates

  • Missing evidence: reject or hold for correction.
  • Critical missing scope or contradictory sources: review.
  • Community/commercial claims cannot set eligibility rules.
  • Manually verify first-POC fees, deadlines and eligibility requirements.
  • Keep candidate, reviewed, published and stale states distinct.
Quality is the main experiment. Select 50–100 manually labelled fields, including German prose, fee tables, exceptions and both degree routes. Compare Qwen with one fallback on the same inputs. Measure field precision/recall, evidence correctness, lost conditions, unknown handling, latency, cost and reviewer effort. Zero unresolved critical errors is a release gate for the reviewed POC, not a claim of universal model accuracy.

Cash budget and effort are different

  • First local POC: $0 incremental hosting bill and a proposed $5 model-usage cap. Existing hardware, electricity and internet are excluded. Free API access may reduce usage charges where available.
  • Optional managed scraping: Firecrawl lists 1,000 basic credits/month free and a $19/month monthly-billed Hobby plan; advanced extraction can consume more credits. Initial collection uses our local HTTP/browser tools. [S5]
  • Later unattended hosting: DigitalOcean lists $24/month for 4 GB / 2 vCPU or $48 for 8 GB / 4 vCPU. Profile PDF memory before selecting. A $30–$70/month envelope is a planning allowance including light usage and backup headroom, not an all-inclusive quote. [S6]
  • Later remote archive: R2 Standard includes 10 GB-month storage plus operation allowances; additional storage is $0.015/GB-month and operations are separate. [S7]
  • Review example: 100 critical claims × an assumed 2 minutes = 3 hours 20 minutes. Two minutes is not a measured rate. Label 50–100 fields first and measure actual review time.

All prices are USD before taxes and currency conversion. Provider prepayment can exceed actual usage. Development, data licences, paid discovery, security/operations work and human review are outside the token estimates. Development effort is unestimated until the first adapter and access checks are complete; labour cost = implementation hours × agreed rate + review hours × agreed rate.

How the application will enforce the cap

Persist spend and usage per run. Before each paid request, reserve a conservative maximum cost using the input estimate and output-token cap. Reconcile with reported usage after completion. Stop dispatching when the remaining budget is insufficient; bound retries and fallback calls. Treat unknown or ambiguous billing responses conservatively. Provider billing settings are separate from this application limit.

08

Build sequence and definition of done

Delivery is milestone-based. A calendar estimate follows the first adapter; website access, PDF layout and reviewer availability are the main unknowns.

  1. M1

    One programme through the entire loop

    Set up the Python package, SQLite migrations, file archive and source registry. Implement one adapter, fetch/parse/extract, evidence checks and a minimal record browser.

    Exit: a real programme has traceable reviewed facts; a repeat run creates no duplicate published facts.

  2. M2

    The bounded Germany dataset

    Extend to three universities and roughly ten programmes with both degree levels represented. Handle structured HTML and at least one representative PDF. Label 50–100 fields and compare extractors.

    Exit: known and unknown fields, source failures and review outcomes are visible; actual model and reviewer costs are recorded.

  3. M3

    Refresh, export and handover

    Add persisted retries, change detection, stale flags, audit diffs and JSON/CSV export. Document setup and a replay from saved snapshots. Demonstrate unchanged-input reuse and a controlled changed-source case.

    Exit: a colleague can reproduce the local run and inspect the exported evidence without relying on the developer’s memory.

Release checklist · proposed, not completed

  • Roughly ten real programme records across the three selected universities, with both intended degree levels represented or a documented source-coverage gap.
  • Every published critical value has a source snapshot, evidence location, applicable scope, timestamp, quality reasons and human review.
  • No unresolved critical errors in the manually reviewed POC release. Report precision/recall and sample size instead of claiming general accuracy.
  • Missing information remains unknown; AND/OR alternatives and exemptions survive extraction.
  • Blocked, failed, conflicting and stale records are visible; affected facts cannot silently become approved.
  • Identical inputs reuse extraction output; refreshed changes create history without duplicate current records.
  • The run report records documents, requests, tokens, cost, failures, coverage and review effort; the application cap is tested.
  • The local browser, export, fresh-machine setup instructions and snapshot replay work.

People and inputs needed

Implementation owner: to assign. Domain reviewer: founder or colleague, to assign. Before the first paid run, choose the universities/programmes, subject mix, named intake(s), source permissions and provider account. The $5 run cap is the planning default; provider account funding and actual usage are separate.

The POC does not require personal student documents or accounts. Later student-facing testing needs its own input, consent and vendor-data decisions. A successful collection demo establishes technical feasibility and a measured data-quality baseline; product usefulness still needs testing with students.

09

How this becomes a country pipeline

After the first loop works, expand to five universities, roughly twenty programmes and up to 200 source documents. Then extend one coverage dimension at a time. Track coverage against the declared institution/programme list and required fields; an exhausted URL queue is not proof that a country is complete.

Shared engine

Fetching, snapshots, parsing interfaces, evidence contracts, validation, scoring, review, budget control, refresh and export remain shared.

Country package

Add official sources, languages, currency/units, qualification routes, jurisdictional rules, applicant context, refresh policy and site adapters. A new country still needs source and rule verification.

Move SQLite tables to Postgres when the team needs shared writes, concurrent workers or hosted access. Add narrative search over approved material when it serves a user task; typed fields continue to drive numeric comparisons. Broader cost-of-living, funding and career modules follow the same evidence contract.

First decision to make: agree the bounded source/programme set and build M1. The source model and collection research already exist; the next useful output is one real, reproducible record with evidence and measured extraction effort.
